# Requirements Tech Plan

用于不同业务项目的需求分析、技术方案生成和实现阶段辅助检查的插件，不绑定特定业务、目录名称或前后端框架。

先根据实际代码确认入口、业务逻辑和数据关系，生成可追溯的方案，待用户单独确认后再实施最小改动。适用于前后端分离、单体服务、多模块以及纯前端或命令行项目；不涉及的页面、后端或数据库章节应注明不适用及原因，不虚构模块。

## 功能

- 识别需求中的高影响歧义并生成精简澄清问题。
- 按实际项目结构召回页面、路由/命令、核心逻辑、数据访问、模型和测试代码位置。
- 生成技术方案文件名和建议 Git 分支名称。
- 管理需求分析、方案确认、代码修改和测试生成阶段。
- 检查技术方案结构、逻辑说明项、表字段说明和代码行号范围。
- 仅允许检查只读 SQL，不执行 SQL。
- 要求数据库接口和数据库之间的映射明确后才能修改相关代码。
- 发生后端/服务端改动时，默认一个需求只生成一个测试文件，并检查生成的测试是否被 Git 暂存。

## 脚本

| 脚本 | 用途 |
|---|---|
| `clarify_requirement.py` | 识别需要确认的需求边界 |
| `collect_evidence.py` | 搜索并缓存跨层代码证据 |
| `suggest_names.py` | 生成技术方案文件名和 Git 分支名，支持 `--slug` 手动覆盖领域短名 |
| `requirement_session.py` | 记录需求阶段，显式调用时检查项目内文件是否允许修改 |
| `generate_plan.py` | 在项目根目录外生成技术方案 |
| `validate_plan.py` | 校验技术方案内容和代码行号 |
| `sql_guard.py` | 用规则筛查 SQL，不执行 SQL，不替代数据库只读权限 |
| `db_mapping_guard.py` | 检查接口到数据库的明确映射 |
| `test_file_guard.py` | 检查测试文件数量和 Git 暂存状态 |

## 使用

显式调用：

```text
$requirements-governor:requirements-tech-plan
```

后面直接跟需求内容即可。插件保持显式调用，不会因普通开发请求自动进入方案流程。

技术方案、SQL 文件和其他生成文档应输出到项目根目录之外。发生后端/服务端改动时，默认只生成测试单元，不编译验证；测试单元需要输出完整业务链路到控制台。没有对应层时，方案应写明不适用及源码依据。

## 适配其他项目

向技能提供实际项目根目录和需求，按现有构建文件、路由、模块与调用关系分析，无需改名或套用固定分层。搜索默认覆盖传入目录的全部模块；大型仓库可重复传入 `--search-root` 限定已确认的相关模块，扫描范围会参与缓存键。脚本会排除常见依赖与构建产物，并支持常见 Java、JS/TS、Python、Go、Rust、C#、PHP 等文本源码。未知技术栈可用定向文本搜索补充，不代表具备这些语言的语义解析器。

文件分层及中英文别名仅用于召回候选，不能当作真实业务结论。中文句子或业务术语未命中时，应从需求提取实体、接口或字段名继续搜索并读取原文。缓存命中后仍需核对当前文件与行号。

## 能力边界

这些脚本是辅助工具，不会自动拦截文件写入。阶段脚本只记录调用方提供的确认文字，不能证明用户真实授权；其中的 `validate-plan` 仅核对文件及哈希，完整结构检查需单独调用 `validate_plan.py`。

澄清问题来自关键词规则；文档生成器需要已编写的实质内容；文档检查不能证明业务正确；数据库映射检查不能证明映射已获授权；测试文件检查不能证明测试覆盖完整。仍需结合当前需求、源码和用户确认作判断。
